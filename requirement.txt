IRIS System Architecture & Documentation 
1. System Overview IRIS is a comprehensive school bus tracking and student management system. The application coordinates between three main user roles: Admins, Parents, and Scanners (bus attendants). It features real-time bus tracking, automated attendance via facial recognition, and dedicated dashboards for each operating role. 
2. Tech Stack 2.1. Backend • Language: Python 3.12+ • Framework: FastAPI (High-performance web framework) • Database: SQLite (iris.db) for lightweight, serverless relational data storage • ORM:SQLAlchemy 2.0+ (Handles all database interactions and schema mappings) • Data Validation & Serialization: Pydantic v2 • Authentication: JWT tokens via python-jose and password hashing via passlib[bcrypt] • Server: Uvicorn • Package Manager: uv (Fast Python package installer and dependency resolver) 2.2. Frontend (iris-frontend) • Language: JavaScript (React) • Build Tool: Vite (Lightning-fast development server and bundler) • Framework: React 19 • Routing: @tanstack/react-router (Type-safe, file-based routing) • Styling: Tailwind CSS v4 (Utility-first CSS framework) • Key Libraries:– face-api.js: Client-side face detection and facial recognition for bus attendance.– leaflet & react-leaflet: Interactive map components for realtime bus tracking.– lucide-react: Modern, consistent SVG icons utilized across the UI. 
3. Database Architecture The backend utilizes SQLAlchemy to define a strongly-typed, relational database schema. Core Tables & Relationships • users: Stores authentication credentials, role (admin, parent, scanner), and basic info.– Relationships: 1-to-many with student_profiles (children) and notifications. • student_profiles: Stores student details (name, roll number, department, photo).– Relationships: Belongs to a parent (User) and assigned to a bus. 1-to-many with face_landmarks and attendance. • buses: Represents school buses with capacity, driver info, route name, and current state (stopped, on_the_way, arrived).– Relationships: 1-to-many with assigned students. • bus_locations: Tracks historical and real-time GPS coordinates of buses including speed and timestamp.– Relationships: Belongs to a bus. • bus_trips: Logs the active journeys of a bus, capturing departure and arrival times. • attendance: Records student presence on the bus (present_in_bus, exited_from_bus).– Relationships: Links student_profiles and buses. • face_landmarks: Stores encoded facial features (JSON arrays) for the facial recognition system.– Relationships: Belongs to a student_profile. • notifications: Stores system alerts strictly bound to a specific user. 
4. Application Workflows & Architecture 4.1. Authentication Flow • Handled securely via standard OAuth2 password bearer flows. • Thefrontend context (AuthContext.jsx) maintains the current user’s JWT and their Role. • Navigation routes automatically protect themselves via layout wrappers, redirecting unauthenticated traffic to /login and role-restricted traffic to appropriate dashboards. 4.2. Frontend Module Breakdown (File-Based Routing) • Admin Dashboard (/admin/*):– Manages the core entities: Users, Students, Buses.– Monitors global Attendance overview.– Performs System Settings & Face Registrations for new students. • Parent Dashboard (/parent/*):– View individual children profiles (/parent/profiles).– Live Tracking (/parent/tracking): Renders a real-time interactive map of the assigned bus using react-leaflet. – View child’s direct attendance records. • Scanner Interface (/scanner/*):– Optimized for a bus attendant or device running the app inside the bus.– Utilizes device camera + face-api.js to scan students entering/exiting the bus.– Creates Face Landmark matches against the database to automate attendance logging without manual intervention. 4.3. Real-Time Tracking & Live Map • Backend API: The bus scanner/driver app posts live GPS coordinates and speed to /buses/{id}/location. • Frontend Tracking: Components like LiveBusMap.jsx receive these coordinates and map them onto a Leaflet map. It visualizes whether the bus is moving, stopped, or arrived based on the reported speed and BusState. 4.4. Facial Recognition Pipeline (Attendance) 1. Registration (Admin): Admin captures a student’s face descriptors (front, left, right profiles) which are encoded and sent to the backend POST /face/register. Stored as JSON arrays in face_landmarks. 2. Scanning (Bus Device): The Scanner route (/scanner/) initializes the camera and loads pre-trained face-api.js models. 3. Matching: When a face is detected in the video feed, the app generates descriptors in real-time, matches them against known student landmarks, and immediately logs the attendance (POST /attendance/mark) to backend if there’s an acceptable confidence threshold, marking the student as present or exited.
